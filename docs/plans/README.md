  no plan. Completeness checklist (advisor's high-level guideline only — a

  1. Project setup: minimal csproj referencing `Expo.ModulesCore`, where the
     module lives in a package (`packages/<name>/dotnet/...` layout).

     `OnStartObserving`/`OnStopObserving`.

  7. Callbacks: `JavaScriptCallback<T>` parameters and their lifetime rules.
  8. JS facade: the TypeScript side (`src/`), typing the native module.
  9. Platform matrix: which platforms, HostFXR (dev) vs NativeAOT (prod)
     loader story, NativeAOT constraints authors must respect (no reflection).
  10. Verification: how to run the module's tests locally
      (`scripts/test-managed.sh`), example-module as the reference.
  11. Troubleshooting: common autolinking/staging failures and where the CLI
      puts artifacts.
  Reference implementation to link throughout: `packages/example-module`.

## Advisor's roadmap assessment (2026-07-08)

Strategic read of `docs/roadmap.md` direction, recorded for future planning
sessions. The operator agreed with this assessment.

- **Sequencing so far is right.** Bottom-up primitive order (values → host
  functions → promises → scheduling → lifecycle → NativeState/HostObject →
  lazy registry), each landing with spec + tests. Keep that discipline.
- **Biggest strategic gap: NativeAOT proof lags surface growth.** The test
  suite exercises only the HostFXR dev loader; NativeAOT compatibility is a
  hard repo constraint but currently a promise, not a proof. Recommend one
  end-to-end NativeAOT proof (example-module, staged via the autolinking CLI,
  running in a real app) BEFORE the next big ABI expansion — retrofit cost
  only grows as ArrayBuffer/SharedObject widen the ABI.
- **Next capability: ArrayBuffer before SharedObject.** ArrayBuffer is mostly
  mechanical (ABI entries + codec, established pattern) and unblocks the
  data-heavy module class (file, camera, crypto). SharedObject carries real
  design risk (registry-backed native identity per the roadmap note) and
  deserves its own design spike after NativeState settles in.
- **CI architecture (operator-decided 2026-07-08)**: two workflows split by
  cost profile. `checks.yml` (plan 001) = fast lane, ubuntu+windows matrix
  (node checks, CLI/TS tests, pure-managed generator tests, format).
  `native-tests.yml` (plan 008) = heavy lane (Hermes cache, testhost, managed
  suite), ubuntu+windows matrix from day one (Windows leg merged into 008
  scope 2026-07-08; ps1 scripts from commit `e380065e` make it cheap). No
  macOS runners for now (dev happens on the operator's Mac; mac runners are
  10× minutes). Future lanes grow as matrix rows in `native-tests.yml`:
  NativeAOT loader lane (vehicle: `apps/hermes-console-app`, gated on the
  E2E proof) → RNW as a separate workflow → Android (incl. Maestro e2e) →
  iOS/macOS last.
  `experiments/*` are hello-world smoke apps — CI ignores them.
- **Windows lane needs a heartbeat.** The repo exists as the
  expo-modules-windows successor, yet desktop-app sits on the RN 0.81 catalog
  while mobile moved to 0.86 (deliberate). Without a periodic Windows E2E
  check, the flagship platform can quietly rot while macOS-hosted Hermes
  tests stay green.
- **After ArrayBuffer: module authoring guide.** API will be stable enough
  that the docs gap becomes the adoption bottleneck (see Direction findings
  above).

## Findings considered and rejected

(So nobody re-audits these.)

- GCHandle leak in `CreateHostFunction`: false — error path releases the
  handle (`Expo.JSI/JavaScriptRuntime.cs`, release on `!result.IsOk`).
- Exception messages propagated to JS: by-design structured error propagation
  per `docs/specs/host-functions-and-errors.md`.
- "Validate raw callback function pointers at the C ABI": not possible;
  rejected as a non-finding.
- `Substring(1)` bounds in generator `LowerCamel`: safe in .NET semantics.
- `int32` overflow in `isValidUtf8` loop: theoretical only; lengths come from
  managed arrays far below `INT32_MAX`.
- Autolinking tsconfig missing strict mode: false — `strict: true` is set.
- CLAUDE.md "effectively empty": false — it is an `@AGENTS.md` include by design.
- Roslyn generator scaling / property-names double loop: no measured cost;
  not worth doing.
- RN 0.81 vs 0.86 dual workspace catalogs: deliberate (RNW requires 0.81);
  at most a doc note when unifying becomes feasible.
- TypeScript version drift (autolinking `~5.9.3` vs catalog `~6.0.3`) and
  transitive advisories in desktop-app build tooling (xmldom HIGH, uuid
  moderate via RNW CLI / expo config-plugins): real but small; excluded from
  the selected plan set 2026-07-08. Revisit if desktop tooling is touched.
